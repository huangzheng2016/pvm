## Highlights

- **`pvm app`: VM programs and web pages as host windows.** `pvm app dev1 -- gedit` or `pvm app dev1 https://example.com` shows a single program or web page from a VM as its own host window through [Xpra](https://xpra.org) 6.5; `ls`, `stop`, `attach` and `config` manage them. Window titles end in the VM name.
  - Web apps of a VM are windows of one Firefox with its own profile, kept apart from the desktop's Firefox, so they share logins, cookies and cache.
  - Clipboard and drops are off until you enable them per VM with `pvm app config`. Host content enters the VM only while one of its windows is in front, never content password managers mark as excluded. Dropped files upload into `~/Downloads` in the VM, and files the VM sends need confirmation on the host.
  - Text typed with a host input method, such as Chinese with Microsoft Pinyin, reaches the app. Known issue: the first word after the Xpra server starts can lose a character, and stray characters were seen once; the cause is not confirmed.
  - The Xpra server listens only on a unix socket in the VM with a per-VM password. Golden images baked from this release on include it; older VMs install it on first use and show the installer's output.
  - Tested on native Windows with WHPX. macOS and Linux hosts start the client, but the host-to-guest clipboard is Windows only; WSL2 is not supported yet.

  See [Apps as host windows](../../README.md#apps-as-host-windows) and the [design](../design/app.md).
- **The Windows installers include the Xpra client.** Both `pvm_windows_amd64_setup.exe` and `.msi` install Xpra 6.5.5 to `%LOCALAPPDATA%\pvm\xpra`. The release job checks the download against a pinned SHA256 and xpra.org's signing key and ships it unmodified with its GPL text and a note on where to get the source. The exe installer was tested installing and uninstalling; the MSI was built but not installed.
- **The `pvm.stream` channel.** Every VM gets a second virtio-serial port that carries host-opened streams to an allowlist of guest targets, so the guest cannot reach the host or the network through it. On native Windows with WHPX it measures 0.6 ms p50 round trips, against a relay path through the gateway that moves about 12 MB/s. `pvm app` uses it, and so does `pvm desktop`, which no longer needs a port map through the gateway VM; the noVNC page now resizes the display to the window and runs at 60 fps. Desktop port maps from older versions are removed. VMs that were running before the upgrade need `pvm stop` and `pvm start` to get the port.

## Fixes

- **UDP on native Windows.** The gateway's QEMU forwarded every port in the 100-port map pool, more sockets than Windows QEMU polls, so the gateway's own UDP failed: DNS to the internet and WireGuard over a UDP exit. The gateway now forwards only mapped ports and updates them over QMP. On native Windows a cluster takes at most 32 maps; the next one fails with an error instead of silently breaking UDP. UDP exits work on native Windows again.
- **New VMs under WHPX.** A new VM first boots with the `qemu64` CPU model until cloud-init has installed the accelerator's kernel arguments, then cold-boots with the full CPU model and checks the running kernel command line. Golden images baked from this release on record their kernel arguments, so their clones skip the cold boot.

## Build

- `script/windows/fetch-xpra-client.sh` downloads and checks the Xpra client; `script/windows/pack-setup.sh` takes its folder as a third argument.
