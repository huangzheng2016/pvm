# Roadmap

Planned work for the next release of this fork. Items move to the release notes once they ship.

## Planned

- **`pvm exit-agent install|uninstall`.** Register the exit agent as a systemd service with one command, like `pvm daemon install` on the host. It writes `pvm-exit-agent.service` with the given `exit-agent` flags, refuses when another agent already holds the ports, keeps the existing token file and certificate so registered hosts need no re-enrollment, and runs `systemctl enable --now`. `uninstall` stops and removes the unit and leaves the token, certificate and registrations in place. Today the unit is written by hand; see [SKILL.md](../SKILL.md#standard-flow-deploy-an-exit-over-ssh).
- **Workspaces.** `pvm workspace` manages a directory between one host folder and one VM in `mount`, `sync` or `copy` mode, with `clone` to download the VM copy. It covers mounting on the native Windows backend through reverse sshfs, and replaces the idea of a `pvm ssh --here` flag with `pvm workspace ssh`. Implemented on master, not yet released; reverse sshfs on native Windows still needs a run against a real VM. See [docs/design/workspace.md](design/workspace.md).
- **A browser and sshfs in the golden image.** Every golden image ships Firefox, installed from Mozilla's APT repository on both Ubuntu and Debian, and `sshfs` for workspace mounts. Ubuntu's `firefox` package only installs the snap, which needs snapd and the Snap Store at bake time and reseeds in every clone, so the provision script adds the Mozilla repository first: it downloads the signing key, fails the bake unless the fingerprint matches, and pins the repository at priority 1000 so the snap transitional package cannot win. Implemented on master, not yet released; confirmed with a real Ubuntu 26.04 bake under native Windows. Only images baked afterwards include them; `pvm image build` rebakes. Mozilla's repository serves both amd64 and arm64. Chrome may become an option later; Google ships its Linux build for amd64.
- **`pvm rm` for a VM whose files were deleted by hand.** When `~/.pvm/vms/<name>` is removed while the VM is still a cluster member, the daemon reports not ready and `pvm rm` fails with "not found". The daemon should log the orphan and stay ready, and `pvm rm` should drop the leftover membership, port maps and gateway link. It must refuse while a QEMU process may still be using the VM's address.

## Candidates

Not yet scheduled.

- **UDP transport under the native Windows backend.** The gateway VM's QEMU user-mode network forwards the whole 100-port map pool for both TCP and UDP, about 200 host sockets. Windows QEMU polls sockets with `select()`, which handles 64 by default, and listening TCP sockets come first, which would explain why UDP replies never arrive. This is not yet confirmed. Confirm by shrinking the forwarded range, then add forwards on demand through QMP `hostfwd_add` when a map is created.
- **`pvm ssh-config <vm>`.** Print an OpenSSH config entry for a VM, with its key, user and a `ProxyJump` through the gateway, so tools such as VS Code Remote-SSH, Mutagen and rsync can reach it by name. It prints only; pvm still never writes to `~/.ssh`.
- **Exit egress probe in `pvm exit test`.** The test only probes the agent itself, so it passes while a VPS firewall drops forwarded traffic. Add a probe that opens a connection to the internet through the tunnel.
- **`pvm app <vm> <url>`: a web page from the VM as a host window.** The page renders in the VM's browser, so cookies, fingerprint and egress IP stay with the VM and its exit; the host only receives pixels. Port maps would load the page in the host browser instead and lose that isolation.
  - Each app gets its own TigerVNC display in the guest running only Firefox in kiosk mode, and its own noVNC endpoint on loopback, reusing the `pvm desktop` stack. noVNC remote resizing keeps the display the size of the host window.
  - Phase 1 needs no host GUI: pvm opens the noVNC URL in a chromeless host browser window (Edge or Chrome `--app=<url>`), which can be pinned like a web app.
  - Phase 2 is a host GUI that hosts the same endpoint in a webview; the guest side stays unchanged.
  - Same access rules as `pvm desktop`: loopback only and VNC authentication. Clipboard and file transfer between host and app are out of scope for phase 1.
  - Optional: cap Firefox memory per app. Disk size hardly matters (about 250 MB installed); RAM does, because by default Firefox starts several content processes per instance, and every app is its own instance.
    - Each app runs Firefox with its own profile directory, so the settings below apply to app windows only and leave the user's desktop Firefox alone. Settings that only work system-wide go in `/etc/firefox/policies/policies.json`; the rest go in each app profile's `user.js`.
    - Single-site settings: fewer content processes (`dom.ipc.processCount`), unloading background tabs under memory pressure (`browser.tabs.unloadOnLowMemory`), and a smaller in-memory cache. Turn off what a kiosk window never uses: telemetry, Pocket, sponsored content, the update check (apt updates Firefox), and the first-run pages.
    - Expose a profile switch, for example `--memory low|default`, rather than raw preferences.
    - Measure before choosing defaults: resident memory of one app window with and without these settings, on a typical web app.
    - Fallback if Firefox remains too heavy: GNOME Web (WebKitGTK) is smaller with acceptable compatibility. Pale Moon and similar forks are lighter but break too many current sites.
  - Considered: Xpra forwards single windows natively but is a heavy and unevenly packaged dependency; Waypipe needs Wayland, while the desktop is X11.
- **A default image and a default VM.** `pvm create --image ubuntu:26.04 --name dev2` repeats the same image on every create, and commands that take a VM name repeat it on every call.
  - Default image: `pvm image default ubuntu:26.04` records it, and `pvm create dev2` then needs only a name, given as a positional argument. With no default set and exactly one distro and version having a golden image, use that one; otherwise fail and list the choices. The create output names the image and golden version it used.
  - Default VM: `pvm default dev2` records it, and VM commands such as `ssh`, `exec`, `desktop`, `map`, `mount` and `workspace` use it when the name is omitted. With no default set and exactly one user VM, use that one. Never guess for destructive commands: `rm`, `stop`, `snapshot restore` and `compact` always require the name.
  - Both live in one host config file written with `fsutil.AtomicWrite`; `pvm rm` of the default VM clears it, and a default image whose base and golden are gone is reported, not silently replaced.
  - One default VM per host, not per directory. Commands that act on an existing workspace already know its VM from the workspace record and use that; the default VM only fills in the name when a workspace is created.
- **Gateway rule drift false positive.** The gateway installs `to <server>/32 iif lo fwmark 0 lookup main`. `ip rule` omits a zero fwmark, so the drift check never matches and re-adds the rule every 10 seconds, logging `restored missing rule` each time.
